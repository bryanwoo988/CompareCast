# 通知提醒：设置界面与数据模型（子项目 A）

日期：2026-09-29
状态：待实现

## 1. 为什么做

用户要按时段收到每个地块的天气提醒：早上决定能不能喷药，下午决定要不要收工。目前应用没有任何通知能力。

这件事是两个独立的子项目：

- **A（本文）**：设置界面与数据模型。设置能存、能改、能自洽，但**通知不会送达**。
- **B（另立）**：推送服务端。VAPID 密钥、订阅注册、Cron 触发、发送逻辑。做完通知才真的会响。

A 的产物正是 B 需要同步上去的那份数据，所以先做 A。

### 为什么 A 单独存在时通知不会响

应用是 GitHub Pages 上的静态站点，没有服务端。应用关闭时唯一能送达的机制是 Web Push，而 Web Push 必须有服务器保存订阅凭证并在指定时刻主动推送。本地定时通知这条路不存在：Notification Triggers API 苹果从未实现、Chrome 已撤回；Periodic Background Sync 仅 Android 且不保证时间。

iOS 另有硬限制：Web Push 需要 iOS 16.4+，且 **PWA 必须已加到主屏幕**，仅在 Safari 中打开页面收不到任何通知。

**这个限制必须在界面上对用户明说**，不能做成一个按了没反应的开关。

## 2. 已确认的决策

用户在 brainstorm 中拍板：

1. **时段全局定义，每个地块只勾选要哪几个时段**。不是每地块各自一套时间。
2. **模式按时段选**：每个时段可以是「每天摘要」或「仅超阈值」。
3. **支持的指标**：降雨概率、降雨量、最高温、最低温、风速、阵风。不做 UV。
4. **阈值全局共用**：喷药的风速上限不随时段变化。
5. **独立全屏页面**，不塞进设置弹窗。

## 3. 数据模型

```js
S.notify = {
  enabled: false,
  windows: [
    {id:'morning',   on:true,  from:'06:00', to:'12:00', at:'06:00', mode:'threshold'},
    {id:'afternoon', on:true,  from:'12:00', to:'18:00', at:'12:00', mode:'threshold'},
    {id:'evening',   on:false, from:'18:00', to:'24:00', at:'18:00', mode:'digest'},
    {id:'night',     on:false, from:'00:00', to:'06:00', at:'00:00', mode:'digest'}
  ],
  rules: {
    rainProb:{on:true,  v:60},   // ≥ %
    rainSum: {on:false, v:5},    // ≥ mm
    tMax:    {on:false, v:35},   // ≥ °C
    tMin:    {on:false, v:22},   // ≤ °C   ← 方向与其余相反
    wind:    {on:true,  v:20},   // ≥ km/h
    gust:    {on:false, v:35}    // ≥ km/h
  }
};
```

每个地块自带 `l.notify`，是启用的时段 id 数组，默认 `[]`。

**阈值一律以公制存储**（°C、km/h、mm），显示时按 `S.units` 换算。这样切换单位不需要迁移数据，也杜绝「35 被当成 35°F」。

`to < from` 表示该时段跨午夜（如 `00:00-06:00`），是合法状态。所有时间比较换算成分钟数进行，不比较字符串。

## 4. 界面

### 4.1 入口与结构

设置页新增一行「通知提醒」，右侧显示摘要（`未开启` 或 `3 个地块 · 2 个时段`），点击进入全屏页 `#notify`（复用 `.page` 的滑入动画与返回逻辑）。

页内自上而下：主开关 → 权限状态 → 时段 → 阈值 → 地块矩阵。

### 4.2 时段编辑器

四张卡片。每张含：名称、启用开关、起止时间（两个 `<input type="time">`）、提醒时间（一个 `<input type="time">`）、模式二段按钮（每天摘要 / 仅超阈值）。

- 关闭的时段**收成一行**，只留名称与开关
- 使用原生 `type="time"`：两个平台都弹系统选择器，自动跟随 12/24 小时制
- `to < from` 时卡片上标注该时段跨天，不视为错误
- 提醒时间不限制必须落在时段内

### 4.3 阈值

六行，每行为「指标 + 开关 + 数值输入 + 单位」。

**最低温是 `≤`，其余五项是 `≥`**。运算符必须显示在界面上，否则必然有人填反。

数值输入按 `S.units` 显示与回写，内部始终存公制。

### 4.4 地块矩阵

表头为各时段短名，其下每个地块一行：名称 + 每个时段一个方块，点击切换。

- **只显示全局 `on` 的时段作为列**
- **点表头切换整列**
- 没有地块时显示提示，引导先添加地点

### 4.5 权限与「现在不会响」

主开关下方：

- 未授权时显示「允许通知」按钮，调用 `Notification.requestPermission()`
- 一段固定说明：设置会保存，但通知目前不会送达；还需要推送服务端；iPhone 必须把应用加到主屏幕
- 「发一条测试通知」按钮，授权后可用，经 Service Worker 立即弹出一条

测试按钮是本期唯一真的会响的东西，用于证明权限与 SW 通路可用。

## 5. 纯逻辑

抽到 `notifylogic.js`：

- `minutesOf(hhmm) -> number` — `'06:30'` → 390；非法返回 -1
- `inWindow(win, minutes) -> boolean` — 跨午夜正确
- `windowSlice(times, dayISO, win) -> {start, n}` — 某日某时段对应的 hourly 索引区间
- `breaches(rules, stats) -> string[]` — 返回超标的规则名

后两个函数子项目 B 的服务端将原样复用。手机端与服务端必须用同一套判定，否则会出现「应用说会提醒但没收到」。

## 6. 边界

| 情况 | 行为 |
|---|---|
| `S.notify` 不存在 | 启动时填入默认值 |
| 时间字段格式非法 | 回落到该时段的默认值 |
| 新增地块 | `l.notify = []`，默认不通知 |
| 删除地块 | 其设置随之消失 |
| `l.notify` 引用了不存在的时段 id | 读取时过滤掉 |
| 全部时段都关闭 | 地块矩阵显示提示，不显示空表头 |
| 浏览器不支持 Notification | 隐藏权限按钮与测试按钮，保留其余设置 |

## 7. 明确不做（YAGNI）

- **推送服务端**：子项目 B
- **UV 指标**：用户明确不要
- **每地块独立时段**：用户明确选择全局定义
- **通知历史 / 已读状态**：没人要求
- **静音日期、假期例外**：等真有需求再说

## 8. 测试

`notifylogic.js` 走 `node --test`，重点：跨午夜的 `inWindow`、非法时间、`breaches` 中最低温的相反方向、空规则。

界面沿用实测方式：

1. 设置页入口摘要随状态变化
2. 关闭的时段收成一行
3. 跨午夜时段显示标注且不报错
4. 阈值在 °C/°F 切换后数值正确换算，存储值不变
5. 地块矩阵只显示启用的时段；点表头整列切换
6. 新增地块默认不勾选
7. 删除地块后矩阵同步
8. 全部时段关闭时矩阵显示提示
9. 未授权时测试按钮不可用；授权后可弹出通知
10. 三种语言文案正确
11. 刷新后所有设置从 localStorage 正确恢复

## 9. 风险

**最大的风险是这个界面会让人以为通知已经在工作了。** 第 4.5 节那段说明不是装饰，是这一期的核心交付之一。实现时不得弱化、不得折叠隐藏。

次要风险：`<input type="time">` 在不同浏览器上的空值与非法值行为不一致，读取时必须校验而不能信任控件。
